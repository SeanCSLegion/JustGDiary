## 1. 条目 1：编辑页按钮逻辑（引用相关）

### 1.1 「段落样式」按钮被引用点亮（= iOS B21）

| | 内容 |
| --- | --- |
| iOS 现象 | 点「引用」之后，左边的**字号 / 段落样式按钮也一起点亮**（B21） |
| iOS 根因 | 高亮判定是"`activeBlock != .body`"，引用也是"非正文"，于是被算进去了 |
| iOS 修法 | 高亮**只认大标题 / 小标题**；同时把点亮状态挂到无障碍的 `isSelected` 上（原来只有底色，旁白与 UI 测试都读不到） |
| Android 现状 | `EditorScreen.kt:257`（与浮层里的 `:301`）把 `activeBlock = EditorBlockStyle.fromPartStyle(currentLine.blockStyle)` 传进格式栏；`DiaryFormatBar.kt:221 / 229 / 238 / 248` 四处都用 **`activeBlock != EditorBlockStyle.Body`** 判定高亮 —— 引用行上 `activeBlock == Quote`，于是按钮被点亮。**同一个 bug。** |
| Android 改法 | ① `DiaryFormatBar` 内部派生 `val styleMenuActive = activeBlock == Title \|\| activeBlock == Heading`，把 221/229/238/248 四处的判据换成它；② `selected = styleMenuActive`（无障碍语义跟着走，这条 Android 已经有了，只是判据要换）。 |
| ⚠️ 陷阱 | **不要**改 `EditorScreen.kt:301` 传给「段落样式菜单」面板的 `activeBlock`：面板用 `style == activeBlock` 决定哪一项打勾（`DiaryFormatBar.kt:350`）。引用不在菜单里（只有大标题 / 小标题 / 正文），所以引用行上"一项都不打勾"才是对的；若把 activeBlock 改成 Body，引用行会在菜单里显示"正文 ✔"。**只改按钮自己的点亮判据。** |
| 测试 | `DiaryFormatBarTest`：现有用例没有断言引用行上的段落样式按钮状态，所以**只增不改**。新增两条：`引用行上段落样式按钮不高亮`（`activeBlock = Quote` → `assertIsNotSelected()`，且底色不是 `secondaryContainer`）、`小标题行上段落样式按钮高亮`（`Heading` → `assertIsSelected()`）。 |
| 文档 | `docs/android-design/04-diary.md` §3.3 的按钮表加一句"段落样式按钮的高亮**只认大标题 / 小标题**"；`docs/android-design/09-test-checklist.md` 的格式栏清单加一条。 |

### 1.2 引用里回车 = 自动取消引用 —— **已确认维持现状，本项不改代码** ✅

**结论（2026-10-01 用户确认）：只有「空的引用行」回车才结束引用；非空引用行回车，新行继续引用。**

| | 内容 |
| --- | --- |
| iOS 现状 | `RichTextEngine.swift:926-935`：只有空引用行（`contentEnd <= lineStart && isQuoteActive()`）才把这一行变回普通空行并消费按键；非空引用行 `handleReturn` 返回 false，交给 UIKit 正常换行，`typingAttributes` 里还是引用的段落属性 → **引用延续**。规范 `docs/editor-format-behaviors.md` R2 的"换行"行也明写"引用延续块样式" |
| Android 现状 | **已经就是这个行为，无需改动**：`EditorModel.blocksNewline`（`:633-637`，本行是空行且是引用 → 吃掉这次回车）+ `endQuoteOnBlockedNewline`（`:645-649`，顺手把这一行改回正文）；非空引用行走 `repairAfterEnter`（`:544-545`）继承上一行 `blockStyle`。两条输入路径都拦（`DiaryEditText.dispatchKeyEvent` + `EditorTextState.onUserText`）；已有用例 `EditorEnterKeyTest:137` `an empty quote line ends the quote when the enter is swallowed` |
| 文档 | `EditorModel.kt:501-510` 的 **D10** 说明**继续有效**（它记的是"空引用行"那条与用户规则 3 的口径调和），**不要改** |
| 若真机上仍看到异常 | 请给一张截图 + 操作序列。最可能的两个分支：① 输入法走 `commitText("\n")` 而不是 `sendKeyEvent`（`onUserText` 那条路的行判定依赖 `fromSpannable` 把末尾空行解析出来）；② 光标停在"引用段**下面**那一行"（那一行自己没有引用样式，回车当然不会结束引用）。这两条都能单独补用例 |

## 3. 条目 3：编辑页居中按钮

### 3.1 ✅ 已确认要修的缺陷（代码可证）：图片行上按钮"可点、状态是错的、点了没用"

| | 内容 |
| --- | --- |
| Android 现状 | `EditorModel.centerAllowed`（`EditorModel.kt:457-462`）只判 `marker == null && blockStyle != quote`，**没有排除图片行** → 光标停在图片行时：① 按钮**可点**；② `isCentered = currentLine.align == ALIGN_CENTER`，而图片行的 `align` 恒为 `null`（`EditorModel.kt:892` 建行时不带 `align`，`linesToParts`（`:226-235`）也不写）→ 按钮显示**未居中**；③ 点一下 → `align = center`，按钮亮起，但**画面逐像素不变**（图片段在 `linesToParts` 里根本不写 `align`），再点一下又灭。**一个会说谎的死按钮。** |
| iOS 对照 | `RichTextEngine.centerIsAllowed`（`RichTextEngine.swift:748-760`）明确把 `bullet / todo / **image**` 三种附件与引用都排除（B24：*"居中改为跳过引用 / 列表 / 图片行（按钮在这些行上本来就置灰）"*） |
| 改法 | `EditorModel.centerAllowed(line)` 补一条 `!line.isImage`；`DiaryFormatBar.centerEnabled` 默认值里的 `!isList && !isQuote && !isTodo` 一并补 `&& !isImage`（两处判据要一致，别只改一处） |
| 测试 | `DiaryFormatBarTest` 的 `center is disabled on list quote and todo lines`（`:71`）扩成四类（加 `image`）；`EditorModelTest` 增一条 `setAlignment 在图片行上拒绝`；顺带钉住"图片段的 `align` 永远不进 `content_json`"（`EditorStateTest.kt:287` 已有同类断言，可挨着加） |

## 5. 条目 5：阅读 / 编辑 / 首页预览显示统一（照 Google 规范）

### 5.1 三个渲染面（iOS 那边是三个：阅读页 / 编辑页 / 周视图预览）

### 5.2 已知的 6 条"编辑 ≠ 阅读"（这就是要收掉的账）

1. **列表 / 待办的标记与缩进**：编辑态是**字面的 `• ` / `☐ ` / `☑ `**（`EditorModel.kt:202-204`），正文体字号，**没有悬挂缩进**（换行后第二行顶到标记底下）；阅读态是 `18dp 槽 + 10dp 间距`（正文起点 28dp，换行也对齐 28dp，`DiaryReadScreen.kt:884-890`、`:550-631`），待办是真勾选框。**这是"编辑时看不到阅读时效果"最明显的一处。**
2. **待办完成态**：阅读态 = 删除线 + `onSurfaceVariant`（`:598-606`）；编辑态只有一个 `☑` 字形，文字不变灰、不划掉。
3. **引用**：阅读态 = `surfaceContainerHigh` 底 + 4dp 圆角 + **左右各 10dp** 内边距，**没有竖条**（`:525-538`）；编辑态 = 同一块底但**只有左边**有 10dp 缩进（平台限制），且当前被 `TEMP-DIAG` 顶着（见 §0）。**另外 iOS 新版已经给引用加了左侧竖条 + 16pt 文字内缩**（`BlockDecorations.swift:30-40`），Android 还没有。
4. ~~**行高**：两边名义行高相同，但基线位置不同~~ —— **实施时核实：这条判断是错的**。
   Compose 的 `LineHeightStyle.Default` 是 `Alignment.Proportional + Mode.Fixed + Trim.Both`
   （`ui-text` 源码），而编辑态正是把 `ascent / descent` **同比例**放大到同一个行高：
   两边是同一条规则，基线位置天然一致，**不需要任何补偿**。真正差的是行盒高度的取整
   （已修：ascent 取整、余数给 descent）与段距（见第 1 条）。
5. **大字号下比例会走样**：`Type.kt:33-44` 对 `fontSize` 与 `lineHeight` **各自**取上限（`effectiveSpForSize`），fontScale=2 时 `bodyLarge` 字号 ×1.55、行高 ×1.45 → 实际比例 1.403（不是 1.500）；`headlineMedium` 1.240（不是 1.286）。两条链路读的是同一个 `TextStyle`，所以彼此还一致，但**离 M3 的比例越来越远**，且没有测试钉住。
6. **第三 / 第四个渲染器各有一套数**：首页日面板（2dp 间距 + `bodyMedium` + 字符串标记）、分享长图（全手写 double，`ShareLayout.kt:108-125`，行高 `×1.17`，引用还带 5px 竖条 —— **竖条只存在于分享图**）。

### 5.3 目标：**一份共享几何** + M3 令牌（不要照抄 Apple 的比例）

**依据（都是可查的 Google / 平台规范，本仓库已经在用同一套）：**

- **M3 字号梯级**（app 编译依赖的 `androidx.compose.material3:material3:1.4.0` 里
  `tokens/TypeScaleTokens.kt`，即 `MaterialTheme.typography` 的官方值）：
  `headlineMedium 28/36`、`headlineSmall 24/32`、`titleLarge 22/28`、`titleMedium 16/24`、
  `bodyLarge 16/24`、`bodyMedium 14/20`、`bodySmall 12/16`。
  **正文 16/24 = 1.50、标题 28/36 = 1.286** —— 与 iOS 新版定的 1.50 / 1.25 本来就几乎重合，
  所以"行高"这一项 Android **不需要动**，要动的是别照搬 Apple 的 `0.55/0.50/0.60×` 段前距。
- **M3 形状梯级**（同包 `tokens/ShapeTokens.kt`）：`extraSmall 4` / `small 8` / `medium 12` /
  `large 16` / `extraLarge 28` —— 引用底圆角 4dp 已经在梯级上（`Radius.bar`）。
- **M3 勾选框**（同包 `tokens/CheckboxTokens.kt`）：容器 **18×18**、圆角 **2dp**、
  未选描边 **2dp / `onSurfaceVariant`**、选中容器 `primary` + 图标 `onPrimary`、图标 **18dp**。
  → 阅读态现在 18dp / 2dp 描边 / `onSurfaceVariant` / `primary` **全对**，只有**圆角 4dp（应为 2dp）**
  与**对勾 14dp（应为 18dp）**两处偏离；而 `docs/android-design/01-design-system.md:137-144`
  写的是"待办勾选框 = small 8dp"、mockup 写的是 2px —— **文档 / 稿 / 代码三方打架，以 M3 的 2dp 收口。**
- **平台 span**（这是 Android 的"官方做法"，`docs/android-design/04-diary.md` §3.2 已经在用同一套）：
  行高 `LineHeightSpan.WithDensity`、悬挂缩进 `LeadingMarginSpan.Standard(first, rest)`、
  段底 `LineBackgroundSpan`、标记字形 `ReplacementSpan`（同一个 span 覆盖现有的 2 个标记字符，
  **字符数不变**，`EditorSelectionTest` / `EditorModelTest` 那批按 2 字符前缀写的偏移断言全都继续成立）。
- **M3 没有的东西要明说**：M3 **不定义富文本段距**，也没有"标记槽"的规范
  （`Type.kt:88-89`、`01-design-system.md:127-128` 已经这么写了）。所以段距只能落在
  **4dp 栅格**上取一个值，并在三处共用 —— 不要再编一套 Apple 的倍数。

**建议的共享几何（一份常量，三处消费）**：
新建 `ui/diary/BlockGeometry.kt`（名字可换），把下面这张表变成**唯一来源**，
`SpannableBridge`（编辑）、`DiaryReadScreen`（阅读）、`HomeScreen`（预览）都从它取值：

| 量 | 建议值 | 依据 / 现状 |
| --- | --- | --- |
| 段间距 | **8dp**（所有块样式统一） | mockup `.rp/.title/.heading{margin-bottom:8px}`、阅读态现状、4dp 栅格；编辑态现状也是 8dp（只是被算进最后一行 descent） |
| 列表 / 待办项间距 | **统一 8dp**（阅读态现在 4dp，要改） | 与段距同值 → 编辑态零特判；备选是维持组内 4dp，代价是 `BlockMetricsSpan` 要判"下一行是不是同一组" |
| 标记槽 / 间距 | **18dp 槽 + 10dp 间距 = 正文 28dp**（三处统一） | 阅读态现状 + mockup `.li .bul{width:18px}` / `gap:10px` |

### 5.4 逐条改法

1. **编辑态标记改成"槽 + 悬挂缩进"**（最大的一项）
   - `SpannableBridge.toSpannable` 给标记行挂 `LeadingMarginSpan.Standard(0, 28dp)`（首行 0、
     其余 28dp）→ 换行后的第二行对齐到正文起点；
   - 标记的 2 个字符（`• ` / `☐ ` / `☑ `）改由一枚 `ReplacementSpan` 画：宽度固定 28dp，
     圆点按"槽内右对齐"、勾选框按"槽内居中 + M3 尺寸"绘制（几何与 `TodoBox` 共用同一份常量）；
   - `fromSpannable` 的解析**不变**（还是认 2 字符前缀），光标 / 选区算术因此不动。
2. **待办完成态**：阅读态与预览已经是删除线 + 变灰；编辑态要补同样的视觉。
   ⚠️ **不能用 `StrikethroughSpan`** —— `fromSpannable` 会把它解析成 `run.strike = true` 写进
   `content_json`（数据污染）。要么用一个**自定义 `CharacterStyle`**（只改 `updateDrawState`，
   解析器认不出它），要么只在编辑态画线不落库；两选一请在设计确认时定。
3. **引用**：按 §5.3 的表把三处的内缩 / 内边距 / 圆角 / （可选）竖条对齐；
   顺手清掉 §0 的 `TEMP-DIAG`；编辑态"右边距挂不上"的平台限制**保留并在文档里写明**
   （`Spannable` 只有左边的 `LeadingMarginSpan`，`SpannableBridge.kt:363-366` 已经记了）。
4. **段距**：编辑态的 8dp **只加在"段与段之间"**（现在最后一段也会多出 8dp，文档末尾会多一截空白）；
   阅读态 / 预览改为同一个 8dp；列表项一律 8dp（见 §5.3 的选择）。
5. **预览面**：`HomeScreen.DayPanelPart`（`:1958-2001`）从"全 `bodyMedium`"改成
   `EditorTypography.textStyleFor(part.style)`，并补上引用底 / 列表槽 —— 它是"缩略"，
   可以只做"字号 + 缩进 + 引用底"三样，但**不能与另两面互相矛盾**。
6. **大字号比例**：决定 `lineHeight` 是否跟随 `fontSize` 的同一个倍数
   （`Type.kt:33-44`），让 M3 的比例在大字号下也成立；这条会动 `DynamicTypeMetricsTest` 的期望值，
   **建议单独一轮做**，别和 1–5 混在一起。
